# 联邦式大数据调度架构设计文档

> **面向场景**：多地区机房（马来西亚柔佛州、中国香港、巴西等）各自部署独立 Hadoop 集群，由新加坡数星平台统一管理的联邦式架构。
> **核心目标**：在跨地域网络不可靠的前提下，保障各区域调度任务准点执行。
> **文档状态**：Draft v0.1

---

## 1. 背景与问题

### 1.1 架构现状

- **新加坡**：部署数星平台，作为唯一中央管理控制台。
- **马来西亚柔佛州、中国香港、巴西**：各自机房本地部署一套完整 Hadoop 集群（HDFS 存储 + YARN 计算），数据与计算本地化。
- **业务约束**：数据不允许跨域传输，各地区之间无任务依赖。

### 1.2 核心矛盾

调度任务要求严格准点，但跨地域网络永远不可能 100% 可靠。若调度触发依赖中心在线（每次到点回新加坡确认“是否该跑”），网络波动将直接导致任务延迟，且延迟随网络抖动不可预测。

### 1.3 设计目标

| 目标 | 优先级 | 说明 |
|------|--------|------|
| 任务准点执行 | P0 | 网络波动不导致任务漏跑或晚跑 |
| 数据本地化 | P0 | 数据零跨域，地区间无数据传输、无任务依赖 |
| 管理集中化 | P1 | 定义、权限、监控、血缘统一在数星 |
| 可观测性 | P2 | 断网期间允许暂时盲区，恢复后补齐 |
| 定义实时更新 | P3 | 断网期间允许定义滞后，恢复后对齐 |

## 2. 总体架构

### 2.1 平面划分

| 平面 | 部署位置 | 职责 | 数据特征 |
|------|----------|------|----------|
| **管理平面 (Control Plane)** | 新加坡数星 | 任务定义、调度策略、权限、监控、血缘 | 仅元数据/控制信息，无业务数据 |
| **数据平面 (Data Plane)** | 各地区机房 | 数据存储、计算、任务执行 | 业务数据本地闭环 |

**关键原则**：管理平面与数据平面物理隔离；业务数据严格本地，不跨域。

### 2.3 管理链路定义

| 链路 | 方向 | 内容 | 断网影响 |
|------|------|------|----------|
| 定义下发 | 数星 → 本地 | 任务定义、cron、依赖、SLA | 新定义无法更新，本地按旧定义继续跑 |
| 心跳上报 | 本地 → 数星 | Agent 存活、集群健康 | 数星失去该地区可观测性，触发告警 |
| 结果回传 | 本地 → 数星 | 任务执行状态、日志元信息 | 结果延迟登记，恢复后补登记 |
| 本地触发 | 本地 Agent → Hadoop | 到点拉起作业 | **不依赖跨域网络，不受影响** |
| ~~跨域数据传输~~ | — | 业务禁止 | N/A |

## 3. 调度架构核心设计

### 3.1 两层职责拆分

调度系统必须拆分为两层，混在一起是事故根源：

| 层 | 职责 | 部署位置 |
|----|------|----------|
| **调度定义面 (Control)** | 任务元信息、定时规则、依赖、SLA 策略 | 新加坡数星（中心） |
| **调度执行面 (Trigger)** | 到点真正触发任务、拉起 YARN/Spark 作业 | **各地区本地集群** |

> **核心原则**：触发动作必须本地自治完成，绝不每次到点跨洋回中心确认。

### 3.2 定义预下沉（预分发）

数星把任务定义提前下发并持久化到本地集群的调度 Agent：

- 本地 Agent 维护一个本地调度表，到点直接触发，不依赖新加坡在线。
- 定义变更走增量下发 + 全量校准双通道。
- 本地持久化采用带版本号的结构，便于断网恢复后对齐。

### 3.3 本地自治触发

每个地区部署一个本地调度 Agent（Airflow Scheduler / DolphinScheduler Worker / 自研 daemon 均可），具备三种工作模式：

| 模式 | 触发条件 | 行为 |
|------|----------|------|
| 正常态 (ONLINE) | 心跳正常 | 从数星同步最新定义，本地按点触发 |
| 断网自治态 (AUTONOMY) | 心跳连续超时 | 继续按本地缓存定义准点触发，不中断；结果暂存本地 |
| 恢复态 (RECOVER) | 心跳恢复 | 补传暂存结果、对齐最新定义、校验漏跑并补跑 |

### 3.4 状态机

```
   ┌─────────────┐   心跳正常      ┌─────────────┐
   │             │ ──────────────▶ │             │
   │  正常态     │                 │  定义同步中  │
   │ (ONLINE)    │ ◀────────────── │             │
   └──────┬──────┘   下发完成      └─────────────┘
          │
          │ 心跳连续超时 (如 3 周期)
          ▼
   ┌─────────────┐
   │             │  ← 本地仍按缓存定义准点触发
   │ 断网自治态  │     结果暂存本地, 等恢复补传
   │ (AUTONOMY)  │     数星侧标记该地区"自治中"+告警
   └──────┬──────┘
          │
          │ 心跳恢复
          ▼
   ┌─────────────┐
   │             │  ← 补传暂存结果 (幂等去重)
   │ 恢复态      │     对齐最新定义
   │ (RECOVER)   │     校验断网期间执行记录, 漏跑则补跑
   └──────┬──────┘
          │
          │ 对齐完成
          ▼
       返回正常态 (ONLINE)
```

### 3.5 时钟与时区

分布式调度对时钟极其敏感，三地区必须：

- **NTP 同源对齐**：建议统一指向新加坡 NTP 主源，本地配备源，避免时钟漂移导致触发错位。
- **时区统一存 UTC**：巴西、香港、新加坡时区不同，cron 与时间戳内部一律以 UTC 存储，展示层转本地时区。
- **拒绝依赖系统本地时间触发**：本地 Agent 取时须校验 NTP 健康度，发现严重漂移立即告警并降级。

### 3.6 幂等与补跑

| 机制 | 用途 |
|------|------|
| 幂等设计 | 任务可重复执行不产生脏数据（覆盖写 / 去重 key），防止“以为没跑→补跑→重复” |
| 本地自检 | 本地 Agent 检测到某任务该跑没跑（进程挂掉等），自动补跑 |
| 中心巡检 | 数星侧“超时未上报成功”巡检，断网恢复后触发补跑 |
| 投递语义 | 至少保证 at-least-once，再用幂等收敛到 exactly-once 效果 |

## 4. 故障场景与应对

| 故障场景 | 影响范围 | 应对措施 |
|----------|----------|----------|
| 单地区 Agent 与数星短暂断网 | 仅该地区可观测性受损 | 本地自治继续触发，数星标记自治 + 告警 |
| 单地区 Agent 进程崩溃 | 该地区触发停止 | 守护进程拉起；自检漏跑后补跑 |
| 数星平台宕机 | 所有地区定义更新与可观测停摆 | 各地区自治继续跑，数星恢复后批量补传对齐 |
| 某地区时钟漂移 | 该地区触发错位 | NTP 健康检查告警，漂移超阈值时降级为保守模式 |
| 定义下发中途断网 | 本地定义版本不一致 | 恢复后走全量校准，按版本号收敛 |
| 结果回传丢失/重复 | 数星侧状态不一致 | 幂等回传（按 `task_id + run_ts` 去重） |

## 5. 可靠性边界

去掉跨域依赖后，调度可靠性的边界非常清晰：

- **唯一风险点**：本地 Agent 与数星之间的管理链路断开。
- **风险后果上限**：仅损失“可观测性 + 定义更新”，**不影响任何任务准点执行**。

只要满足以下三个前提，网络波动对“任务准点跑”这个目标基本可被工程消化：

1. 任务定义已预下沉并持久化在本地；
2. 本地 Agent 能自治触发并自治判断失联；
3. 时钟同步到位（NTP 同源 + UTC 存储）。

## 6. 选型与落地检查清单

### 6.1 平台选型必问清单

在选型或评估数星平台时，必须确认以下问题：

- [ ] 任务定义能否预下发到本地持久化？
- [ ] 本地 Agent 断网后能否继续自治触发？
- [ ] 断网期间执行结果如何补登记，会不会重复触发？
- [ ] 时钟同步和时区处理机制是什么？
- [ ] 是否本质上是“每次到点都由中心主动调起远程任务”的中心化触发模型？（若是，跨洋场景不可用）

### 6.2 落地前提清单

- [ ] 各地区本地调度 Agent 部署完成
- [ ] 本地任务定义存储格式与版本机制确定
- [ ] 失联判据（心跳超时阈值）确定
- [ ] NTP 同源配置完成
- [ ] UTC 统一存储策略落地
- [ ] 幂等键（`task_id + run_ts`）规范确定
- [ ] 结果补传协议（去重 + 重试）确定
- [ ] 故障演练计划（断网注入测试）排期
